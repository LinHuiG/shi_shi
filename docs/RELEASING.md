# 发布流程

当前公开仓库为 `LinHuiG/shi_shi`，主分支为 `main`，首次发布版本为 1.2.0。首次导入从已审查的源码快照建立全新 Git 历史，不迁入私人开发历史、分支、标签或运行文件。仓库可见性仅按维护者明确指示设置，构建脚本不得自动修改。

1. 检查源码、提示词、文档、测试、作者元数据和 staged 文件；不得包含真实聊天、人名、账号、内网地址、客户事项或私人配置。
2. 运行 Rust 与全部 UI 回归及 DSH 工作区桥测试（见 DEVELOPMENT.md），确认全新安装使用通用参数，AI 接入和用途模型留空，未配置时不调用模型或消耗额度；扫描、消息过滤、自动分析及自动更新默认开启，完整 AI 跟踪和“仅分析相关消息”默认关闭。归档只维护归档记忆，提示词与规则仅人工采用；旧自动采用开关不再生效。API/ACP 测试只使用 mock，不把真实供应商兼容性写成已验证。
3. 执行 `python scripts/check_release.py`。脚本同时检查已跟踪和未忽略的未跟踪文件，新增 `src/`、`assets/`、`providers/` 源码不能靠尚未 `git add` 逃过 allowlist/隐私扫描。该扫描是有限规则，不替代人工审查和专业密钥检测。
4. 使用 `python scripts/package_source.py` 从已审查的 Git 跟踪文件生成源码 ZIP；未提交变更必须先审查提交。脚本拒绝敏感路径和未审查文件类型，不复制整个工作目录。
5. 构建安装器，在隔离目录安装，检查文件清单、README 与 EXE 哈希、启动和退出。检查实际二进制字符串、资源和截图；源码干净不代表旧二进制干净。
6. 检查 Cargo.lock 依赖安全公告、许可证及 `vendor/wry` 本地改动。工具签名和正式发布签名另行准备，不把哈希校验称为代码签名。
7. 发布时只选用本次已验证的指定产物，不上传整个 build 目录或开发期间截图。

个人或企业专用词典不得写进公共扫描脚本，转义形式也不例外。需要额外检查时，将 UTF-8 文本文件放在仓库外，通过 `SHISHI_PRIVATE_TERMS_FILE` 指定；每行一个按字面匹配的词，忽略空行和以 `#` 开头的注释，匹配不区分大小写。未指定时只运行公共规则；指定但不可读取时检查失败，不回显词典内容或路径。私有词典不进入源码包。

## 首发范围

只推送允许清单中的源码、合成测试、配置模板和文档；不上传安装包、历史 ZIP、日志或任何运行状态。Git 作者使用账号对应的 noreply 邮箱，避免泄露私人联系地址。不包含相邻的插件项目。

## 公开发布前仍需核实

- 标识图片与全部 vendored 资源的来源和再分发权利。
- 最新依赖安全公告及 Windows/WebView 适配。
- 安装器签名、干净环境的安装验证、最终二进制和截图扫描。
- 仓库历史、标签、Release 附件和 CI 日志均符合隐私要求。
- GitHub 的安全报告渠道可用，README 中的已验证范围与实际测试一致。

这些事项不能仅凭源码测试通过就标记为完成。

## 更新资源

正式 Release 的安装器和摘要须遵循 [版本更新说明](UPDATES.md)。本地准备阶段不创建远端标签或发布资源。打包时自动生成编译时间，并核对实际解析的 WebView2 加载器与构建指标。
