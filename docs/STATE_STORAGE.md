# 业务数据存储

1.2.2 起，当前数据目录中的 `state.sqlite3` 是业务状态的权威副本。配置使用 `settings/<uuid>.json`，图片继续使用文件。旧 `state.json` 留作升级前备份，正常提交不再重写它。

## 提交与读取

`state_store::Store` 持有一个由应用互斥锁保护的连接，启用 WAL 和 FULL 同步。消息、事项、审计、归档版本、报表、建议修订和处置轮次分别按记录保存；每条记录保留自己的 JSON payload，供业务模型演进使用。消息时间、审计所属事项和时间有独立列与索引。这里没有把整份旧状态作为一个数据库字段保存。

`metadata` 保存其余状态，包括来源、消费游标和关联状态。一次业务提交在同一事务中更新记录与 metadata，提交成功后才发布候选内存状态。配置变化先写入新的 JSON 文件并同步，再在事务中切换引用；事务失败时旧引用仍有效。旧配置版本只在持有独占安装转换锁与数据锁的启动阶段清理，避免删除正在被其他读取者使用的版本。

消息列表与事项历史在数据库中筛选和分页，同一读取事务返回总数及当前页，避免计数和页面来自不同提交。历史搜索保留原有词匹配规则。MCP 通过只读事务加载与当前版本一致的状态。

运行时的大集合使用 `Shared<T>` 共享快照，未修改的集合不会因候选状态复制而复制数据。保存时跳过未修改的集合，对发生变化的集合比较记录内容，只写入变化行。首次打开 Store 时读取已有行建立比较基线。

当前运行时仍在启动时载入完整业务状态；修改某个集合时，写时复制和记录比较仍随该集合规模增长，Store 也保留序列化比较缓存。此次改造降低了常规保存的磁盘写入与无关集合复制成本，没有实现全量惰性加载或与数据规模无关的内存开销。关键词搜索也不是全文检索索引。后续优化应以实测热点为依据，逐步替换相应业务接口。

## 升级与故障边界

安装器先等待旧进程退出并确认文件可替换，然后使用新包中的迁移助手处理当前数据目录，成功后才替换程序。启动时保留同样的迁移检查，支持直接更换程序或自定义数据目录。

迁移先解析受支持的旧格式，在独立目录建立数据库，执行完整性检查并进行全部业务状态的语义往返比较。检查通过后移动配置版本，最后发布数据库。原 JSON 不删除；失败保留原数据并中止，不以空状态继续。这里不改变既有不兼容的预发布格式处理规则。

`pending_import` 记录旧 JSON 摘要。在新程序首次正常保存前，如果安装中断后旧程序又写入了 JSON，下次迁移会重新导入；首次正常提交后删除标记，SQLite 成为权威副本，后续不会再次覆盖为旧 JSON。数据库版本不支持、配置引用失效或加载失败时停止加载，不静默回退或重建。

数据目录迁移在独占锁下先 checkpoint 并关闭 WAL 模式，再复制业务库和配置文件。迁移后的托管工作目录引用通过 Store 提交；旧目录保留。备份业务库应在应用退出后复制完整数据目录，不能在运行中只复制主数据库文件。

## 验证入口

`state_store` 单元测试覆盖旧状态和关联内容往返、安装中断后的旧写入、首次新提交后的权威切换、两万条消息下单行变更只触发一次 UPDATE、分页及记录与游标一起回滚。既有归档、处置、保存失败与目录迁移用例继续检查原业务语义。

原生升级验收使用隔离的旧版安装和合成数据，检查升级后事项、配置、原 JSON 摘要及 SQLite 完整性。测试行写入数量只能证明增量提交行为，不能代替不同设备上的延迟与内存基准。
