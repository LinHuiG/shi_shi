## SS-045 Windows 11 真 Mica 背景（P3）

- 依据：Windows 11 应用的底层材质为 Mica。现在用实色 `#202020` 模拟其回退色。真 Mica 需要透明窗口和透明 WebView2，并在 tao 窗口上调用 DWM 背景材质，例如 `window-vibrancy` 的 `apply_mica`（Apache-2.0/MIT）。
- 风险：只支持 Windows 11 22000 及以上。用户关闭透明效果、省电模式、窗口失焦或硬件较弱时，系统会回退为实色。透明 WebView 中的文字可能从 ClearType 降为灰度抗锯齿。需要新增依赖，并检查 HiDPI 黑边和窗口圆角。
- 方案：作为可选增强，默认保持实色。检测到 Windows 11 且系统透明效果开启时，启用透明窗口加 Mica，页面底层改为透明，内容层保持现有不透明层色，失焦时回退为实色。设置中提供开关。
- 验收：Windows 10/11、关闭透明、对比度主题、125%/150% 缩放下文字清晰度和回退表现正常，拖动和缩放不卡顿；关闭开关后与当前实色版本一致。
- 实施（用户于 2026-10-19 要求引入）：不新增依赖，用现有 `windows-sys` 的 DWM 接口设置深色非客户区和 `DWMSBT_MAINWINDOW`。配置 `window_backdrop` 默认开启、重启生效；开启时窗口和 WebView 透明。系统返回失败时记录 `backdrop_unavailable`，页面保持不透明；系统确认成功后才给页面打上 `data-backdrop="mica"` 标记，此时只有底层和侧栏透明，内容区为 30% 的 Fluent 层色，卡片仍不透明。减少透明度和对比度主题下回到实色。自检（smoke）模式始终不透明。
- 状态：已实施（2026-10-19），Windows 实机待验证。`palette-ui.cjs` 断言了不透明回退与透明底层；Windows 目标 `cargo check` 和容器内 Rust 测试通过。以下都需在 Windows 11 实机确认：实际 Mica 效果、透明 WebView 下的文字清晰度、Windows 10 回退、拖动和缩放流畅度，以及 `color-scheme: dark` 是否让 Chromium 画出不透明底色（若出现，Mica 不可见，但界面不受影响）。

## SS-036 前端工程化与状态推送（P1）

- 证据：前后端在协议层已分离（`window.ipc.postMessage` JSON-RPC，`src/main.rs` 的 `dispatch` 约 69 个方法，测试已用模拟 IPC 独立运行前端）。耦合在构建与数据流：前端 5 个文件在编译期由 `include_str!` 拼接嵌入，任何 UI 修改都需重编 Rust；样式为单行压缩的叠加覆盖；前端每 3 秒轮询完整 `state` 快照，`Engine::snapshot` 持锁克隆并排序全部相关消息。
- 作用域：前端源码组织、构建产物嵌入方式、状态同步协议。不改为本地 HTTP 服务（会引入端口暴露、鉴权与 CSRF 面，且失去 WebView2 原生集成）。
- 方案：前端拆为独立目录（按页面/组件分模块，样式按 token/组件分文件），构建输出单一产物供 Rust 嵌入；开发模式从磁盘加载并复用现有模拟 IPC，前端迭代无需重编 Rust。状态同步改为后端推送变更版本号，前端按需拉取增量，取代 3 秒全量轮询。
- 验收：现有 UI 回归套件全部迁移并通过；安装包仍为单一程序；空闲时 IPC 流量与快照克隆次数显著下降（给出前后对比数据）。
- 遗留范围：承接 SS-035 的旧样式覆盖层合并清理，随前端拆分一并完成。
- 2026-10-19 方案分析：保留原生 JavaScript 与现有 IPC，先按页面/组件拆分源码和样式并建立构建入口，迁移现有模拟 IPC 回归；再用后端变更通知合并刷新、按页面读取数据，移除周期性完整 state 拉取。通知版本需覆盖持久状态、AI 进度、来源及工作状态，不能只用现有审计 revision；时钟和跨日派生状态单独更新。订阅后首次同步、窗口重新显示及版本不连续时可重新拉取；编辑草稿独立于展示快照，刷新不能覆盖草稿。分别统计空闲 IPC 次数/字节、快照耗时和持锁时间作为前后对照，不预先承诺无实测的降幅。
- 实施：界面源码移至 `assets/ui/`，`manifest.txt` 定义组装顺序；内联脚本按页面拆为 core/tasks/settings/reports/logs/forms/events/boot，与原有 4 个扩展按原顺序在同一作用域拼接，与拆分前逐字节等价。`build.rs` 组装后嵌入，`--ui-dir` 从磁盘组装，`tests/ui-bundle.cjs` 供 UI 测试使用，三者共用同一清单。样式拆为 token、布局、设计层，删除 364 条被同一 media 上下文中相同选择器后续覆盖的失效声明；8 个页面加对话框、1280/900 两种宽度共 1,355 个元素的计算样式逐一相同。另加按用途命名的灰阶别名；不支持 `backdrop-filter` 或用户要求减少透明度时，浮层回退为不透明材质。
- 状态同步：通知线程每秒比较变化指纹，覆盖状态修订号、保存次数、运行标志、AI 进度、活动记录、在途消息和分钟刻度，有变化才推送；去掉前端 3 秒轮询，窗口重新可见时补拉一次。`state` 只返回核心快照，处置记录、审计、报表和迭代建议按页面请求，messages 不再随快照发送。事项状态时间改为单次构建的审计索引。编辑草稿沿用原有保护：编辑中或对话框打开时不重绘。
- 未做：空闲 IPC 次数/字节、快照耗时和持锁时间的前后实测对照，需要在 Windows 实机采集，本轮没有采集，所以不宣称具体降幅。
- 状态：已完成（2026-10-19）。Rust 测试在 mingw + wine 容器中按 Windows 目标运行，失败集合与改动前基线一致，均为 DPAPI、WinHTTP、Job 对象、mklink、PowerShell 等 wine 不支持的能力。新增测试全部通过；11 套 UI 回归通过，其中 `state-sync-ui.cjs` 为新增；`cargo fmt --check` 和发布扫描通过。尚未在 Windows 实机运行，也未构建安装包。

## SS-037 c30725c 代码审查结论

来源：对 `061ebf6..c30725c` 的只读审查（未在 Windows 编译运行，结论来自代码阅读；前两项已人工复核）。按严重度排列：

- 中｜`src/main.rs` 边界线程：`work_boundary_tick` 失败时仍推进 `previous`，跨越下班或早报边界的那次 tick 若保存失败，当天边界永久错过，仅留错误日志。建议仅成功后推进，失败保留旧值（受现有 120 秒间隔保护约束）。
- 中｜`src/managed_data.rs`：写入中断残留的 `state.next.json` 会被检查为不兼容数据，即使 `state.json` 完好也阻断启动。建议无法解析的临时文件静默删除。
- 中｜`src/engine.rs` / `src/archive.rs`：每次 AI 请求在持有全局状态锁时重建消息、事项、审计快照，序列化并回读 JSONL 校验，期间 UI 轮询与写操作全部阻塞。建议锁内只取 revision 与必要字段，构建与校验移到锁外，或按 revision 缓存。
- 中｜`archive_versions`、`morning_jobs`、`archive_attempts`、`day_records` 无保留上限；每组归档带完整提示词。叠加每次修改全量 clone 与每次保存全量序列化，体积与耗时随使用线性增长。建议按数量或天数裁剪，提示词按内容去重引用。
- 低｜`ai_key` IPC 路由无调用方，且绕过 `credential_id` 间接引用与地址变更须重填密钥的规则，建议删除。
- 低｜`src/archive.rs` 的 `queue_attempt` 分支不可达，若启用会因无对应 claim 而必然失败，建议删除或复用 `end_attempt_id`。
- 低（待确认）｜`providers/acp/src/client.rs` 经 cmd 启动 `.cmd` 时未处理 `%`，路径含 `%VAR%` 会被展开。
- 低（待确认）｜`src/ai_backend/dsh.rs` 以整段 JSON 字符串包含 `read_context` 判断补查能力，应按工具 name 精确匹配。
- 设计确认｜不兼容数据经用户确认后直接删除 `state.json` 与备份（AGENTS 已声明预发布数据不迁移，非缺陷）。建议改为移动到带时间戳的 legacy 目录，降低误操作代价。
- 设计确认｜补查每页有上限、累计无上限，单次分析可读入整个快照，仅受 600 秒与 8 MB 约束；需确认是否满足“上下文查询保留范围与大小限制”。

性能建议（与 SS-036 合并实施）：后台 6 个线程与前端 3 秒定时器合计约每秒一次全量 `state`，快照内对每个事项扫描两遍审计（O(事项×审计)）并携带 60 份完整报表；改为 revision 推送、可见时按页面分块拉取；`save` 直接 `to_writer` 并以 rename 代替复制备份；审计预建 `task_id → 最后状态变化` 索引；`analysis_context::query` 缩页改为长度估算加二分。

- 历史回归待核对：SS-035 曾记录事项标记完成后仍留在待处理列表的 UI 断言失败；后续 SS-041 记录 10 套 UI 回归通过。需先核对该场景是否已覆盖及问题是否仍存在，不直接视为当前已确认缺陷。
- 2026-10-19 代码复核与方案：
  - 调度：已确认 main.rs 在 work_boundary_tick 返回错误后仍推进 previous。用户已确认：保存失败时在原边界的 120 秒窗口内重试；超窗跳过并明确提示手动处理，不扩大补跑范围。重试成功后才推进成功时间，边界 claim 与任务记录保持同一保存事务；超窗后记录可见的遗漏原因并恢复正常后续 tick，避免永久重试旧边界或重复执行。故障注入覆盖短暂失败、超窗、恢复与重复 tick。

## SS-086 DSH 拒答结束原因被包装为内部协议错误（P1）

- 实施：DSH 适配层将可识别的 refusal 映射为“供应商拒答”，API 同步识别 refusal/content_filter；保留未知内部错误及原始错误，不自动重试或应用不完整结果。

## SS-088 AI 超时配置、上游 504 与前后端等待一致性（P1）

- 状态：已完成并纳入 1.1.1（2026-10-19）；实施与离线验证结果见本节末。
- 实施：增加一个全局 ai_timeout_seconds，默认统一 600 秒，范围 30—1800 秒；Codex、DSH、API 共用。DSH 会话设置与提示请求共享剩余期限，API 工具及纠正循环沿用单一截止时间。长操作改为短 IPC 接受及按编号查询终态，避免通用 300 秒等待误报。504 单独说明上游网关限制。
- 证据：当前 API 的整轮分析期限固定为 600 秒，涵盖工具循环、格式降级及纠正请求；API 客户端与 WinHTTP 参数校验亦限制最多 600 秒，没有用户配置入口。DSH 分析期限同为 600 秒，Codex 分析子进程为 240 秒。前端通用 IPC 等待为 300 秒，超时只移除等待项，不取消后台 AI；长操作可能先报前端超时、后收到后台完成状态。记录中的 504 为上游实际 HTTP 状态，并非本地整轮期限触发；整轮耗时不能用于推定单次 HTTP 或网关的固定期限。
- 方案：采用一个全局 AI 总时限，默认 600 秒，Codex、DSH、API 的分析请求共用，不按来源或连接分别配置，明确区分连接等待、首包等待、流中空闲及整轮总时限；范围为 30—1800 秒；保留单一总期限，不增设分别配置。若支持超过 600 秒，须同步调整客户端、HTTP 层及前端边界，不只增加一个无效配置字段。前端长操作优先返回请求编号，再以状态持续追踪最终结果与取消，不因通用 IPC 等待结束而暗示后台已终止。日志区分本地超时、IPC 等待超时和上游 HTTP 504。
- 处理边界：延长 SS 本地期限不能延长上游网关期限；上游慢请求可由用户核对网关限制、选择已配置且支持的较低推理强度、调整输入预算或显式重试。流式传输可能减少空闲等待引起的断连，不能保证消除上游总时限。暂不增加自动拆分续批或整轮自动重试。
- 验收：离线覆盖配置默认值、保存重启、非法值及各层边界，HTTP 504、本地期限、长连接持续输出、无进展、跨工具轮次及取消；前端等待超过 300 秒后能追踪同一后台请求，迟到事件不污染下一请求。所有阶段和纠正共享总期限，失败不推进分析进度、不伪造用量。

## SS-108 来源显示名称变化导致已分析消息重复入队（已定位，仅登记）

- 反馈（已泛化）：消息过滤提前触发的分析请求包含已分析的跨日旧消息，并遇到上游 HTTP 504。公开记录只保留复现关系，不保留真实请求数量、消息及服务信息。
- 证据：`context_budget.rs::pending_for` 按可配置的滚动回看小时数选取，默认 24 小时，不以自然日切断；`pending_all` 排除已成功分析且完整消息指纹未变的消息，但未分析或指纹变化的旧消息仍可入选。关联未归档事项的会话也可纳入候选范围，不限于直接涉及用户的单条消息。`classify_with_task_limit` 首次请求不自动注入旧消息正文，但携带未归档事项摘要，需要时可只读补查旧证据。`engine.rs` 仅在成功调用、校验并提交结果后更新已分析指纹，504 不会标记本批已处理。日志 `ai_start.messages` 统计 changes 条数，不是全部上下文条目数。
- 通用复现：先成功分析消息集合 A，再修改来源显示名称；重新读入 A 时仅 source_name 不同，旧完整指纹仍会把 A 识别为变化，并与尚未分析的集合 B 一同入队。A、B 可以跨自然日，但仍满足滚动回看范围。该集合示例不对应真实消息、数量或调用时刻。
- 根因：`model.rs::fingerprint` 序列化整个 Message，含展示字段 source_name；`sources.rs::normalize` 使用来源当前显示名称覆盖该字段。扫描既读取增量又回查跟踪依据，来源名改变会使重新读入的旧消息与已分析指纹不同，继而被误当作待分析变化。消息过滤器也共用该指纹；不是消息正文实际新增了上百条，也不是单纯上下文计数。
- 后续条件：请求因 504 失败或被取消时，旧消息仍保留为待分析；随着旧消息滑出滚动窗口和新消息到达，后续候选集合可能变化。不能仅凭批次大小推断 504 的上游原因。
- 用户最新修订：消息变化指纹只包含消息本体、是否撤回；回复与快捷回复不再作为独立指纹因素，替代此前包含二者的要求。其余字段一律不参与指纹，不自行扩展到接收对象等元数据。来源名称、群名、发送者显示名称、时间、本地缓存路径及独立回复关联字段等变化均不得单独触发重新分析。消息身份仍用于区分不同消息，不等于把身份字段作为消息变化依据。
- 回复边界：回复作为新消息按其自身身份入队，其本体变化按本体识别，不因某条消息被回复而重新发送原消息；已有 reply 关联信息仍可用于理解上下文，不因排除出指纹就删除。现有通用模型有独立 reply 字段，尚未确认各插件是否把引用内容或快捷回复全部嵌入正文，不把这一假设记录为已核实事实。
- 范围与验收：消息过滤与完整分析使用上述同一变化口径；消息本体或撤回状态发生变化时能够识别，其他字段单独变化时不重传。设计兼容已有指纹的处理，避免升级造成全量重算或静默标记真实未处理消息。覆盖重命名来源及群名、回查旧依据、已有指纹、本体编辑、撤回、回复作为新消息入队、仅回复关联变化不重传原消息及跨日场景。仅登记调查结论及用户修订，未修改程序或安装数据。
- 补充边界：Message 的 group 等显示字段也参与当前完整指纹；群名更新若被插件回传并写入旧消息，也会产生同类误判，但范围限于实际重读、满足回看与候选条件的消息，不能断言群内全部历史都会重传。现场已确认的直接原因是来源显示名称变化。

## SS-109 消息过滤提前触发标记在失败或中断后未消费（已定位，仅登记）

- 用户要求：消息过滤的提前分析决定仅触发一次，不以完整分析成功为消费条件；完整分析失败或人工中断，不得反复复用同一次过滤决定发起请求。
- 通用复现：消息过滤给出提前分析决定后，让完整分析失败或人工中断，再等待下一次调度；没有新的过滤调用时仍重复启动 message_filter 请求，且提前触发标记保持为 true。关闭扫描不会清除此标记。公开记录不保留实际操作时刻或调用次数。
- 根因：`engine.rs` 仅在完整分析成功提交后清除 message_filter.early；失败或取消路径保留该标记。`analyze_after_scan` 将 early 与常规到期条件作 OR，导致常规 due_reason 中的人工中断等待保护被绕过，只剩 60 秒最小间隔。`tick` 每轮都调用分析调度；扫描开关仅由 scan_tick 判断，关闭扫描不关闭对已有队列的自动 AI 分析。
- 范围：把提前触发决定作为一次性请求，在实际开始完整分析时消费并保留准确触发日志；失败或中断保留待处理消息但不得以旧决定重复提前执行。新的真实增量可有新的过滤决定，常规分析间隔单独遵守既有调度及中断规则。明确扫描与自动分析开关的作用，避免用户误以为停止扫描会停止全部 AI；不得擅自把二者永久绑定。
- 验收：同一过滤决定仅启动一次完整分析，成功、504、校验失败及取消均不导致该决定再次触发；人工中断等待保护不被旧提前标记绕过；关闭扫描后的行为符合明确的开关语义；并发新决定不会被旧请求清除，重启不会复活已消费决定，未处理消息不丢失。仅登记分析与用户要求，不实施功能修改。

### SS-126 全局快速平滑显示

- 证据：各页大量直接替换 innerHTML；现有分析动画包含首段、长段、非前缀变化和结束时直接覆盖的分支，多个浮层及展开区没有过渡。已获上述逐项实施授权。
- 范围：共享稳定 DOM 更新、短时可中断动效、按真实标识复用动态列表、保留表单/阅读/展开状态；异步结果保留可用旧内容。减少动态效果时直接更新。所有值与操作立即生效，动画不延迟数据或权限决定。
- 验收：各确认项覆盖正常变化、快速连续变化、重复快照、上翻阅读、输入中更新及窄屏；不累计动画、无陈旧控件或重复发送。

### SS-127 返回结果后的未知短编号错误缺少 AI 终态记录

- 状态：已确认实施。私有输入/输出和日志只在本地只读核对，不写入公开源码或记录。
- 泛化证据：模型返回完整 JSON，在 create.task_id 中自行填入未分配的短编号；反解将其误按已有事项引用拒绝。反解错误和部分保存错误通过 `?` 提前退出，绕过 ai_failed 记录，只剩开始记录与通用错误。不能将该情形表述为供应商未返回完整内容。
- 范围：新建事项由程序分配 ID，清空其不参与业务引用的模型占位字段；更新目标及所有证据引用继续严格校验。响应后校验/保存收束到明确终态日志，记录请求关联、已返回标志与失败阶段；旧孤立开始记录只表示尚无结束记录。
- 验收：用合成新建占位、未知更新目标和未知证据验证边界；调用实际响应收尾路径，确认校验失败有同请求编号的 ai_failed，且没有 ai_success。不自动重放实际资料或修改已安装数据。
